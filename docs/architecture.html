03

Architecture overview

ทุก component ในภาพเดียว

อ่านภาพนี้อย่างไร

Client → Edge → API

เข้าได้ 2 ทาง แต่ทุก request ผ่าน Load balancer + CDN เข้าสู่ API ชุดเดียวกัน

API แบบ stateless

process เดียวที่แบ่ง module ภายในชัดเจน รันอย่างน้อย 2 ตัว เพราะไม่เก็บ state ในตัวเอง

Worker

ใช้โค้ดชุดเดียวกับ API แต่รันแยก process รับงานช้าจาก queue เช่นแจ้งเตือน ปิดโพล ดึงรูป

Source of truth

Postgres เป็นแหล่งข้อมูลจริงเพียงแห่งเดียว Redis เก็บเฉพาะข้อมูลที่หายได้หรือสร้างใหม่ได้

06

Flow การทำงาน

5 เส้นทางหลักของระบบ ตั้งแต่ login จนปิดโพล

A

เข้าใช้งาน

เข้าจาก CUNEX

เมนู, notification หรือลิงก์แชร์ CUNEX เปิดเว็บเราพร้อม ?token=

เปิดเว็บตรง

กด "เข้าสู่ระบบด้วยบัญชีจุฬาฯ" → login ที่ CUNEX → กลับมาพร้อม ?token=

Google / Email

ได้ user ที่ is_chula_verified = false ตอบได้เฉพาะโพลสาธารณะ

API เอา token ไปแลกที่ /profile (แนบ ClientSecret ฝั่ง server) → บันทึกหรืออัปเดต user และคณะ → สร้าง session → ตอบ 302 พร้อม httpOnly cookie ไปยัง URL ที่ไม่มี token ติดอยู่ หลังจากนี้ไม่ต้องติดต่อ CUNEX อีก

B

สร้างโพล → อนุมัติ → เปิด

  1. สร้างร่างบันทึกโพล, element และตัวเลือก สถานะเป็น draft
  2. รูปภาพถ้าอัปโหลดไฟล์ client จะอัปโหลดตรงไป object storage ด้วย presigned URL ถ้าใส่ URL รูป worker จะดึงรูปมาเก็บไว้ในระบบเรา
  3. ส่งขออนุมัติสถานะเปลี่ยนเป็น pending_review และขึ้นในคิวของ Admin
  4. Admin ตัดสินบันทึกผลใน poll_reviews และ audit_logs ถ้าตีกลับ สถานะเป็น rejected แก้แล้วส่งใหม่ได้
  5. เปิดโพลโครงสร้างถูกล็อก แล้วส่งงาน 3 อย่างเข้า queue: สร้าง UniversalLink · ส่ง notification ให้ user ที่อยู่ในขอบเขตเป็น batch ตามโควตา · ตั้งงานปิดโพลที่เวลา closes_at
C

โหวต / แก้คำตอบ

  1. เช็กเวลาสถานะต้องเป็น open และเวลาปัจจุบันยังไม่เลย closes_at ต้องเช็กเวลาด้วย เพราะ worker อาจปิดโพลช้ากว่ากำหนด
  2. เช็กสิทธิ์คณะและปีเข้าของผู้ใช้ต้องตรงกับ poll_audience_rules
  3. เช็กคำตอบตอบข้อบังคับครบ ตัวเลือกเป็นของคำถามนั้นจริง จำนวนที่เลือกไม่เกินกำหนด
  4. สร้าง voter_keyคำนวณ HMAC(pepper, poll_id‖user_id) ในหน่วยความจำ แล้วทิ้ง user_id ไม่ส่งลง DB
  5. Upsertบันทึกใน transaction เดียว: ยังไม่เคยโหวตจะสร้างใหม่ · เคยโหวตและเปิดให้แก้จะแทนที่คำตอบเดิม · เคยโหวตแต่ไม่เปิดให้แก้จะตอบ 409
i

ระหว่างที่ผู้ใช้กด "ถัดไป" ทีละหน้า คำตอบอยู่ฝั่ง client ทั้งหมด จะส่งมาครั้งเดียวตอนกดส่ง

D

ดูผล

สิทธิ์

ใครเห็นผลเมื่อไหร่

เจ้าของโพลเห็นได้ตลอด · ผู้ตอบเห็นได้ทันทีถ้าเปิดแสดงผลเรียลไทม์ ถ้าไม่เปิดต้องรอโพลปิด

Cache

Redis 3 วินาที

ถ้าไม่มีใน cache ค่อยรัน GROUP BY และคนที่ขอพร้อมกันรอผลจาก query เดียวกัน ผลคือ 5,000 คนทำให้ DB ถูก query แค่ประมาณ 1 ครั้งทุก 3 วินาที

Privacy

k-anonymity

ผลแยกตามคณะหรือปี ถ้ากลุ่มไหนมีคนตอบน้อยกว่า k คนจะไม่แสดง

E

ปิดโพล

ถึงเวลา closes_at worker จะเปลี่ยนสถานะเป็น closed และแจ้งผลได้ถ้าต้องการ ถ้า worker ทำงานช้า ขั้นตอน C.1 ยังกันโหวตหลังหมดเวลาได้ เจ้าของกดปิดโพลก่อนกำหนดได้

07

การไม่ระบุตัวตนและข้อมูลส่วนบุคคล

ซ่อนตัวตนจากเจ้าของโพล แต่ยังกันโหวตซ้ำและแก้คำตอบได้

มาตรการกันอะไร
ballot ไม่มี user_id มีเฉพาะ voter_keyแค่ได้ข้อมูลจาก DB อย่างเดียวจะรู้ไม่ได้ว่าใครตอบอะไร
pepper อยู่ใน secret manager ไม่ได้อยู่ใน DBDB backup ที่รั่วออกไปเอามาย้อนหาตัวตนไม่ได้
เวลาโหวตปัดเป็นนาทีเอาเวลาไปเทียบกับ log การ login แล้วเดาตัวคนไม่ได้
k-anonymity ตอนแสดงผลแยกกลุ่มกลุ่มที่มีคนตอบ 2–3 คนเดาตัวตนไม่ได้
ห้ามบันทึกการโหวตใน audit log และ app loglog ไม่กลายเป็นช่องทางเชื่อมคนกับคำตอบ
ดึงรูปภายนอกมาเก็บเอง ไม่ hotlinkserver รูปภายนอกไม่เห็น IP ของผู้ที่เปิดโพล
ไม่เก็บ studentId เก็บแค่คณะและปีเข้าลดปริมาณข้อมูลส่วนบุคคลที่เก็บ ตามหลัก PDPA
Token ของ CUNEX ใช้ครั้งเดียว แล้ว redirect ไป URL ที่ไม่มี tokentoken ไม่รั่วผ่าน Referer หรือ history
