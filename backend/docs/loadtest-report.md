# Load test: Vercel + Supabase (31 ต.ค. 2569)

ทดสอบ backend บน **staging ที่ตั้งค่าเหมือน production** (Vercel region sin1, Supabase ฟรี ap-southeast-1, `DATABASE_POOL_MAX=1`, session ใน Postgres) ไม่ได้ยิง production

ตัวยิงโหลดรันจากเครื่องเดียวในไทย เน็ตไปสิงคโปร์ใช้ ~50ms ต่อรอบ (เวลาทุกตัวด้านล่างรวมส่วนนี้แล้ว)

## วิธีทดสอบ
- ผู้ใช้ทดสอบ 2,000 คน พร้อม session ([`loadtest/seed.mjs`](../loadtest/seed.mjs))
- โพลทดสอบ 3 หน้า: เลือกตอบ 1 ข้อ, เลือกได้หลายข้อ, ตอบเป็นข้อความ
- ตัวยิงโหลด [`loadtest/run.mjs`](../loadtest/run.mjs) จำลองคนที่:
  1. เปิดหน้าโพล
  2. ตอบ 3 หน้า (หยุดคิดหน้าละ 1–3 วินาที)
  3. ส่งคำตอบ
  4. ดูผล
- ทุกหน้าเรียก API แบบเดียวกับที่หน้าเว็บเรียกจริง (`/me`, `/polls/:id`, `/faculties`)

## ผล
| รอบ | คนพร้อมกัน | request/วินาที | p50 | p95 | p99 | error | คำตอบที่ส่ง |
|---|---|---|---|---|---|---|---|
| 1 Smoke | 5 | 7 | 106ms | 196ms | 263ms | 0% | 23 |
| 2 โหวตปกติ (4 นาที) | 100 | ~150 | 99ms | 150ms | 221ms | 0% | 1,857 |
| 3 Spike (0→300 ใน 30 วิ) | 300 | ~450 | ~105ms | ~170ms | – | ถูก Vercel บล็อกตั้งแต่วินาทีที่ ~45 | – |
| 4 ดูผลเรียลไทม์ | 200 ดูผล + 30 โหวต | ~40 + ~45 | 116ms | 179ms | 261ms | 0% | 451 |
| 5 เพิ่มทีละขั้น | 100 → 200 → 250 | 150 → 300 → 380 | 99ms | 154ms | 222ms | 0% | 4,035 (สูงสุด ~1,000 คำตอบ/นาที) |

**ความถูกต้อง:** หลังรอบ 1–3 จำนวนคนที่ส่งคำตอบสำเร็จ (ไม่ซ้ำคน) ตรงกับจำนวนแถวใน `ballots` พอดี (1,857 = 1,857) ไม่มีคำตอบซ้ำหรือหาย ทุกคำตอบครบทุกข้อ

**ฐานข้อมูล:** query ที่ใช้บ่อยสุดเฉลี่ย 0.02–0.13ms (`pg_stat_statements`) ฐานข้อมูลยังเบามาก

**Cold start:** request แรกของเครื่องใหม่ช้าสุด ~2.0–2.3 วินาที

## สรุป
1. **ถึง 250 คนพร้อมกัน (~380 request/วินาที) backend ยังไม่ช้าลงเลย:**
   - p95 นิ่งอยู่ ~150ms ตลอด
   - เวลาส่วนใหญ่คือเน็ต (~50ms) บวกการเรียกฐานข้อมูลหลายรอบต่อ request
   - **ยังหาจุดพังของ backend ไม่เจอ** เพราะติดเพดานของตัวยิงเอง (ข้อ 2)
2. **ยิงจาก IP เดียวเกิน ~450 request/วินาที Vercel จะบล็อกอัตโนมัติ:**
   - ขึ้นหน้า "Vercel Security Checkpoint" (`403`, `x-vercel-mitigated: challenge`) แล้วปลดเองใน ~8 นาที
   - ผู้ใช้จริงมาจากหลาย IP จึงไม่น่าโดนแบบนี้
   - **แต่มีความเสี่ยงหนึ่งจุด:** หน้าเว็บ (Next.js) เรียก API จาก server ของ Vercel เอง ทั้ง render ฝั่ง server และ rewrite `/api/v1` ถ้าโหลดสูงมาก request เหล่านี้อาจมาจาก IP ของ Vercel ไม่กี่ตัว และโดนบล็อกแบบเดียวกัน ทำให้ทั้งเว็บใช้ไม่ได้ ควรทดสอบเส้นทางผ่านเว็บด้วย หรือรวมเว็บกับ API ไว้โปรเจกต์เดียว
3. **คิดเป็นการใช้งานจริง:** 1 คนใช้ ~1.5 request/วินาทีระหว่างตอบ ที่ 380 request/วินาทีเท่ากับคนกำลังตอบพร้อมกัน ~250 คน หรือส่งคำตอบได้ ~1,000 คำตอบ/นาที (60,000 คำตอบ/ชั่วโมง) โดยยังไม่เห็นว่าช้าลง
4. **Redis:** หลังย้าย session ไป Postgres แล้ว Redis ใช้แค่ตอนส่งคำตอบกับดูผล ไม่ใช่คอขวด

## ยังไม่ได้ทดสอบ
- ยิงจากหลาย IP เพื่อหาจุดพังจริงของ backend
- เส้นทางผ่านหน้าเว็บ Next.js (`cunex-poll.vercel.app`) ซึ่งมีการ render ฝั่ง server เพิ่มอีกชั้น
- การอัปโหลดรูป

## วิธีรันซ้ำ
```bash
DATABASE_URL=<staging session pooler> API=https://<staging-api> ORIGIN=<APP_ORIGIN ของ staging> \
  node loadtest/seed.mjs 2000 seed.json
node loadtest/run.mjs seed.json --mode journey --stages 60s:100,180s:100 --out result.json
node loadtest/run.mjs seed.json --mode watch --stages 20s:200,160s:200
```
`seed.mjs` ไม่ยอมรันกับฐานข้อมูล production และไฟล์ `seed.json` มี session ของผู้ใช้ทดสอบ อย่า commit
